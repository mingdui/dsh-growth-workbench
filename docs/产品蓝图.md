> 版本：v0.1 → v2 的路线图　状态：**提案**（本文描述的方向除第一节基线外，均未实现）
> 配套：[产品文档](./产品文档.md) 讲现状与规则，[架构文档](./架构文档.md) 讲实现与接缝。

## 〇、一句话赌注

> **模型越来越会「说得很像学会了」。所以「能被检查的证据」会越来越值钱。**

这条赌注决定了产品的整个形状：

| 常见做法 | 本产品的做法 |
|---|---|
| 记录你学了什么 | **要求你交出什么** |
| 展示进度百分比 | **分开报完成率与证据质量**（合成一个数就不可复现） |
| 用 AI 生成鼓励 | **用 AI 当验收方**，只凭自述不能把「了解」提升为「掌握」 |
| 让你在应用里待更久 | **让你用两分钟就离开，去干活** |

**推到底**：一个个人成长产品的价值不在于它说了什么，而在于**它不接受什么**。

## 一、现在在哪（v0.1 实测基线）

不是愿景，是已经跑过的数字：

| 维度 | 现状 | 说明 |
|---|---|---|

| 方向目录 | 9 个（preset 1 / building 3 / beta 5） | 后 8 个**没有锚点**，页面如实标注颗粒度更粗 |
| 路线 | 3 条（稳妥 / 冲刺 / 系统） | |
| 计划结构 | 两段式：近期排到天、后续排到周 | |
| 任务合同 | 8 字段，缺一不算拆完 | 写入门禁强制 |
| 考核 | 四维各 25 分 · 4 档定级 · 8 行反馈表 · 5 条铁律 | |
| 打卡 | 每日勾选 + 证据 + 档位（自述 / 过程 / 成果） | |
| 数据 | 4 份 JSON 在 `$DSH_HOME/growth-workbench/` | 页面与 Agent 共用 |
| 入口 | 左侧菜单整页（4 页签）+ 右侧「今日」Tab | |

**一句话现状**：一条**完整但单方向**的闭环。规则是真的、验收是真的、门禁是真的；**内容只有一条路**。

## 二、未来全景

```
                          用户的一天
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
   打开页面看一眼         跟 AI 说一句话         被提醒
   （2 分钟）             （"考核我"）          （到点了）
        │                     │                     │
        ▼                     ▼                     ▼
┌───────────────────────────────────────────────────────────────┐
│  第一层 · 执行面   今日打卡 · 证据 · 档位 · 连续天数             │  ← 已存在
│                    「今天只做这一件，最低完成版本也认」          │
├───────────────────────────────────────────────────────────────┤
│  第二层 · 判断面   计划生成 · 四维考核 · 调整版任务 · 归因       │  ← 已存在
│                    能力曲线 · 作品达标度对照 · 知识考核抽题      │     曲线未画
├───────────────────────────────────────────────────────────────┤
│  第三层 · 校准面   能力模型校准 · 锚点行业校准 · 场景库          │  ← 缺失（最大瓶颈）
│                    真人复核 · 同路人互评 · 招聘方口径            │
├───────────────────────────────────────────────────────────────┤
│  第四层 · 衔接面   作品集 ↔ 真实 JD · 模拟面试 · 简历证据链      │  ← 缺失（价值出口）
│                    面试官视角的追问 · 转岗后的前 90 天           │
└───────────────────────────────────────────────────────────────┘
        │                     │                     │
        ▼                     ▼                     ▼
   平台能力：能力模型包 · 提醒调度 · 曲线可视化 · 多方向并存 · 导入导出

                    ▲                              ▲
                    │                              │
            用户贡献的校准数据              其他客户端（非 DSH）
            真实转岗结果回流                数据格式是 JSON，谁都能读
```

**读图要点**：

- **第一、二层已经通了**——这是 v0.1 的成就：闭环成立，且**闭环里的每一步都有强制约束**。
- **第三层是瓶颈**。缺了它，产品在 9 个方向里有 8 个只能"按通用框架粗着做"。
- **第四层是出口**。用户要的不是"完成率 85%"，是**换到一个新岗位**。第四层把已完成的作品接到真实招聘口径上。
- **横向三块是杠杆**：不加方向、不加模型，靠平台能力就能让现有内容的价值翻倍。

## 三、三条主线

未来所有工作都能归到这三条之一。**它们互相解锁，顺序不能反。**

### 主线 A · 内容：从一个方向到一条赛道

```
数据运营（唯一）
   │  ① 把 ROLES 从代码里搬出来，成为数据包
   ▼
能力模型包：{ 方向, 组, 项, 权重, 1/3/5 锚点, 场景库 }
   │  ② 补齐 building 的 3 个方向（产品运营 / 用户运营 / QA Agent 开发）
   ▼
4 个可逐项自评的方向
   │  ③ 把 beta 的 5 个方向逐个升到 preset
   ▼
9 个方向都能逐项落点
   │  ④ 允许第三方提交方向包（像 LWB 的能力包那样挂载）
   ▼
方向不再由我们决定
```

**为什么第一步是"搬出代码"**：现在加一个方向要改 `model.mjs`、跑自检、重装。搬成数据后，加方向 = 放一个文件。**这是所有后续内容工作的前提。**

**每加一个方向必须同时给**：4-5 个组（权重合计 100%、每组 > 0%）、每项 1/3/5 锚点原文（**不得有"待补"占位**）、6 个左右真实场景。给不出 5 分锚点就是还没落地——把状态留在 `building`，别硬凑。

### 主线 B · 判断：从"打分"到"校准过的打分"

```
四维 rubric（现在是硬编码的分数段）
   │  ① 曲线可视化（数据已齐）
   ▼
看得见的趋势
   │  ② 作品达标度对照真实 JD 口径
   ▼
考核与现实对齐
   │  ③ 锚点由在职的人复核（"欢迎在职的人纠正"）
   ▼
判断有外部校准
   │  ④ 同路人在同一条赛道上互评作品
   ▼
判断不完全依赖我们
```

**这条线的意义**：现在的判据是初稿，需要够格的人来纠正。**把"初稿"变成"被校过"是产品可信度的来源。** 一个自称能判你够不够格的产品，如果判据从没被够格的人看过，它凭什么？

### 主线 C · 衔接：从"计划完成"到"岗位到手"

```
计划 + 作品集（已有）
   │  ① 作品集 → 简历素材（把证据链翻译成简历语言）
   ▼
简历上每一条都能指回一件可检查的作品
   │  ② 对着真实 JD 做差距复核（不只是对着能力模型）
   ▼
"我离这个岗位还差什么"有了外部锚点
   │  ③ 模拟面试：按考核自查题与作品追问
   ▼
答不上来的地方 = 真实的补强清单
   │  ④ 转岗成功后继续跑 90 天（新人期）
   ▼
产品生命周期从 90 天延长到 180+
```

**这条线是产品的价值出口**。前两条线让"每天都在做对的事"，这条线让**做完之后能换成什么**。

## 四、版本路线

| 版本 | 主题 | 交付 | 解锁了什么 |
|---|---|---|---|
| **v0.2** | 让现状可用 | 曲线可视化 · 考核提醒（定时器）· `scope` 简报按阶段裁剪 | 长时间跑得下去 |
| **v0.5** | 内容扩容 | **能力模型搬出代码成为数据包** · 补齐 3 个 building 方向 · 场景库 | 从"一个方向的产品"变成"一条赛道的产品" |
| **v1.0** | 对齐现实 | 作品集 ↔ JD 复核 · 简历证据链 · 模拟面试 · 曲线按能力项分组 | 用户能拿着它去面试 |
| **v2.0** | 社会化 | 锚点外部复核 · 第三方方向包 · 同路人互评 · 多方向并存 | 内容与判断不再由我们独占 |

### v0.2 详情（最近的一版）

| # | 项 | 为什么现在做 | 依赖 |
|---|---|---|---|
| 1 | **能力曲线可视化** | 数据已经齐（`curvePoints` 带 `来源` 与 `置信度`）；缺的只是画。**而且规则已经定好**：定向轮不画线、不带来源与置信度的点不许画 | 无 |
| 2 | **考核提醒** | 宿主端本来就是有生命周期的 Cordis 插件；调整项里已经写了下一次考核日期。**"到点"从一句话变成一个动作** | 无 |
| 3 | **`growth_context` 按阶段裁剪** | 任务多时 `scope=all` 会很长。按阶段过滤，让 Agent 只读该阶段 | 无 |
| 4 | **调整项定形状** | 现在 `adjustments` 是自由数组，工具只校验它是数组。定形状后可以**按调整项直接改计划任务** | 无 |

**v0.2 的共同点**：不新增内容，只把已有内容的**最后一公里**接上。

### v0.5 详情（决定产品天花板的一版）

| # | 项 | 关键约束 |
|---|---|---|
| 1 | **能力模型包化** | 包格式 = `{ slug, name, status, positioning, groups[], items[{ id, group, name, level, anchors[3] }], scenarios[] }`。挂载方式参考 LWB 的能力包：目录约定 + 清单校验 |
| 2 | **校验器随包走** | 组权重合计 100%、每组 > 0%、锚点非占位、`高` 权重项 8-10 项 —— **装包时校验，不合格拒绝挂载** |
| 3 | **补齐 building 3 个方向** | 每个都要真实锚点，不能是"照着数据运营改词" |
| 4 | **场景库** | 每个方向 6 个左右真实场景，用来把实战项目挂到具体问题上 |
| 5 | **状态自动推导** | 有锚点 → `preset`；只有定位 → `building`。**状态不再手写**，避免"标了 preset 却自评不了" |

**这一版之后，"产品能做什么"不再由我们写死。**

## 五、北极星与反指标

### 北极星

> **完成一次真实转型的人数**（而不是"使用产品的人数"）

拆成可观测的三件事：

| 指标 | 想要的方向 | 说明 |
|---|---|---|
| **第 30 天还在打卡的比例** | 高 | 90 天计划的第一个真门槛 |
| **交出的 `成果` 档位证据数** | 高 | 这是产品唯一不可伪造的产出 |
| **方向调整次数** | **低**（且集中在前期） | 方向每周至多调一次；后期还在大调 = 当初的画像没问清 |

### 反指标（增长不可以牺牲它们）

| 反指标 | 为什么它是反的 |
|---|---|
| **人均使用时长** | 用得越久越糟。产品应该每天两分钟，剩下时间去干活 |
| **日活 / 打开次数** | 打开次数高可能只是计划碎得太细 |
| **自述档位证据的占比** | 占比升高说明验收在放松 |
| **越权降级的次数** | `planStart` 退化成"首次打开日"、`任务标识` 缺失 —— 这些都是**静默变错**，出现即视为事故 |
| **同一份计划被反复生成的次数** | 生成得快不代表生成得对 |

**一条硬规矩**：**任何以"提升留存"为名、放松证据要求或降低门禁的改动，一律不做。** 一个"好用的"成长产品很容易退化成打卡玩具——玩具不会让人转型成功。

## 六、最大的瓶颈：能力模型

产品在 9 个方向里的能力分布：

```
preset  ████░░░░░░░░░░░░░░░░  1 个   逐项自评 + 逐题落点 + 加权缺口
building ████████░░░░░░░░░░░░  3 个   只有一句定位，按通用框架粗着做
beta    █████████████░░░░░░░░  5 个   通用模板，未经行业校准
```

**现有机制对非 preset 方向的降级是诚实的**（页面标注、状态字段、`unresolvedGroups`），但降级本身就是损失：

| 缺锚点导致失去的能力 | 影响 |
|---|---|
| 逐项自评 | 只能按通用框架问，读数不可比 |
| 加权缺口 | 没有权重就没有 gap，补强优先级为空 |
| 逐题落点 | 考核的知识维只能笼统判，不能按项判定 |
| 能力曲线 | 没有稳定的项集，跨轮不可比（**不是不能画，是画了没有意义**） |

**为什么锚点这么难**：1 分 / 3 分 / 5 分必须是**同一个尺子上的三个真实刻度**，而且 3 分要是真实的"岗位达标线"。这需要**真的做过这个岗位的人**参与 —— 不能由模型代笔。

**所以 v0.5 的真正难点不是代码，是内容来源。** 三条路：

1. **公开资料 + 在职复核**：先起草，再请 2-3 位在职的人逐项纠正 —— 对应 skill 里那句"欢迎在职的人纠正"
2. **招聘口径反推**：从真实 JD 里抽能力项，但**注意 JD 写的是要求，不是能力刻度**，需要进一步拆
3. **用户回流校准**：跑完 90 天、真的转岗成功的人，他们的自评曲线与最终结果**就是最硬的校准数据**

第 3 条是长期最值钱的那条：**产品跑得越久，锚点越准**。这也正是它值得做数据包的原因——校准数据要能回流到包里。

## 七、护城河：证据不可伪造

如果只能留一条护城河，是这条：

```
自述  <  过程  <  成果
口头说   草稿/笔记   可检查的产出（链接 / 仓库 / 报告 / 截图）
```

**为什么 AI 时代这条会升值**：

| 趋势 | 后果 |
|---|---|
| 生成文本的成本趋近于零 | "我学会了"这句话的信息量趋近于零 |
| "AI 帮我做完了"变得寻常 | 只有**可检查的产出**还能区分人 |
| 招聘方开始要作品 | 作品集比简历厚更有说服力 |

产品已经在这条线上做了三件事，且都是强制的：

1. **证据档位是三值枚举**，不进空档
2. **`evidence` 为空 → `tier` 强制回落 `null`**（不默认成"自述"）
3. **完成率与证据质量分开报**，合成一个"真实完成率"就两边都不可复现

**下一步（v1.0）**：让证据**可核**——不只看有没有，还要对着 `完成标准` 与 `可接受证据` 逐条核。现在这一步靠 Agent 读文字判，将来可以：
- 对**链接类**证据做可达性与时效校验
- 对**代码类**产出对能力项做静态特征检查
- 对**报告类**产出核"问题-方法-结论"三段是否齐（这正是 rubric 作品达标度维的判据）

**原则不变**：这些是**增加核验强度**，不是增加门槛形式。不能让"交证据"变成一个填表仪式。

## 八、明确不做的事

这些不是"暂时不做"，是**产品定位的边界**。

| 不做 | 为什么 |
|---|---|
| **不承诺结果** | 不说"3 个月一定转成功"。给路径与验收标准，不给 offer |
| **不编造薪资数字与来源** | 薪资一律标"估算"；资源链接无法确证就标"未确证" |
| **不做登录 / 云同步 / 多设备** | 数据是本机 JSON，用户自己就能拿走 —— 这正是它能被信任的原因之一 |
| **不代写简历 / 不自动投递** | 工具给你判断，不替你出手 |
| **不做陪伴式教练** | 产品给机制，不给情绪劳动。**"加油"不是功能** |
| **不因一次失败劝退** | 一次低分只触发对应机制，绝不产出"你不适合这个方向" |
| **不替用户判断能力** | 答不上来记 `null`；**不替他填 1 分，也不填 0 分** —— 两种填充都会凭空造出差距 |
| **不把用户变成数据** | 校准数据回流必须匿名且用户知情；不做"你的成长数据用来训练模型"这种默认勾选 |
| **不为了留存放松门禁** | 见第五节的反指标 |

## 九、风险

| # | 风险 | 表现 | 应对 |
|---|---|---|---|
| 1 | **内容供给跟不上** | 9 个方向长期只有 1 个能逐项落点 | v0.5 包化 + 外部复核；宁可少而实，不要多而虚 |
| 2 | **锚点失真** | 3 分不是真实达标线，导致 gap 系统性偏高或偏低 | 必须由在职的人复核；用真实转岗结果回流校准 |
| 3 | **退化成打卡玩具** | 完成率好看，作品栏空的 | 反指标监控；`成果` 档位证据数是北极星之一 |
| 4 | **用户搬不动数据** | 数据在本机、无同步，换机器就"丢了" | `GET /gw/api/export` 一次导出全部；文档里写清路径 |
| 5 | **单向绑定 DSH** | DSH 变了产品就得跟 | 数据是格式稳定的 JSON，领域层无 Harness import；换宿主只需重写两端传输 |
| 6 | **AI 判分不稳定** | 同样进度两次考核分数差很多 | rubric 给的是分数段与判据，不是自由发挥；`confidence` 与 `unsubmitted` 强制区分"判了"与"没数据" |
| 7 | **计划生成质量波动** | 同样画像两次生成的计划差很多 | 8 字段合同 + 天区间 + 标识分配全部由门禁强制；**结构恒定的部分不交给模型自由发挥** |
| 8 | **用户想被鼓励** | 觉得产品"太冷" | 这是定位不是缺陷。冷的是规则，不是语气——对事不对人：说"这个任务安排得不合适"，不说"你执行力不行" |

## 十、里程碑一览

```
v0.1 ─── 已完成 ─────────────────────────────────────────────────
        闭环成立：画像 → 计划 → 打卡 → 考核 → 调整
        门禁成立：8 字段 / 天区间 / 标识永不复用 / 四维 0-25
        双端成立：页面与 Agent 共用一份数据

v0.2 ─── 让现状可用 ────────────────────────────────────────────
        曲线可视化 · 考核提醒 · 旧数据导入 · 简报裁剪 · 调整项定形状

        能力模型包化（含装包校验）· 补齐 3 个方向 · 场景库 · 状态自动推导
```
